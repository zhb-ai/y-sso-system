## 当前 E2E 用例“覆盖度”与改进缺口（面向端到端业务链路）

> 说明：本仓库当前是 Playwright 端到端用例（没有开启 c8/istanbul 等代码覆盖率产物），因此这里的“覆盖率”以“业务链路是否被真实执行 + 断言是否能证明链路结果正确”为准。

### 用例总览（按 spec）

| Spec | 目前覆盖的链路（概括） | 主要断言强弱 | 关键缺口 |
|---|---|---|---|
| `login.spec.js` | 登录页元素存在性 | 只验证 UI 存在 | 缺少“登录成功/失败”的结果断言（及错误提示） |
| `sso-login.spec.js` | SSO 登录页元素存在性 + 已登录展示入口 | 只验证入口出现 | 缺少“未登录/无效登录状态”的负向断言 |
| `dashboard.spec.js` | 仪表盘基础元素存在性 | 仅检查可见 | 缺少搜索/过滤/分页等真实交互与结果断言 |
| `settings.spec.js` | 系统设置基础元素存在性 | 只检查可见 | 缺少“保存/刷新”实际操作与结果断言 |
| `cache.spec.js` | 缓存管理基础元素存在性 | 只检查可见 | 缺少“刷新”实际操作与结果变化断言 |
| `roles.spec.js` | 角色 CRUD + 搜索 + 删除 + 权限分配抽屉打开/关闭 | 抽屉只开不做 | 缺少抽屉内实际选择权限、提交/确认、以及权限状态的结果断言 |
| `users.spec.js` | 用户 CRUD + 搜索 + 启用/禁用 + 角色分配对话框“取消” | 角色分配只取消 | 缺少在对话框内选择角色、确认、以及用户列表/用户详情映射变化断言 |
| `applications.spec.js` | 应用管理 CRUD（含“生成配置”步骤的部分校验） | CRUD 有一定结果校验 | 删除后的列表刷新/一致性断言可以更强；关键字段（如密钥/配置生成）缺少强校验 |
| `organization.spec.js` | 组织架构树节点展开/收起 + 部门 CRUD | 成功提示有一定校验 | 创建/编辑/删除后树节点是否出现/消失的断言偏弱（文中也多处注明“可能不刷新”） |
| `employees.spec.js` | 员工 CRUD + 部分搜索 | 创建/编辑有表格断言 | 删除后表格一致性断言偏弱；少量地方仍依赖固定 sleep |
| `sso-roles.spec.js` | SSO 角色 CRUD + 搜索/状态筛选 + 删除 | 基础操作覆盖较完整 | 删除/筛选后的“表格内容变化完整性”断言仍可加强 |

### 建议的“最低可接受覆盖标准”（用于后续迭代）

1. “打开弹窗/抽屉/对话框”必须升级为至少一条“关键业务动作”（例如：保存/确认/选择并提交）。
2. 对“成功消息”之外，必须至少断言一次“数据/列表/表格内容发生变化”（不要求端口数据全量，但要能证明后端变更被 UI 反映）。
3. 登录/鉴权类用例至少包含：
   - 正向：使用有效账号能进入受保护页面；
   - 负向：无效账号/无 token 能进入登录页或触发兜底重登逻辑。

### 优先级（按收益）

- P0：角色权限分配、用户角色分配（缺“完成业务动作 + 结果断言”）
- P1：dashboard/settings/cache 的关键交互（缺“保存/刷新/搜索结果变化断言”）
- P2：组织架构/员工删除后的 UI 一致性断言（降低误通过/脆弱性）
- P3：鉴权兜底的 token 失效场景（证明 `smart-auth.js` 的兜底逻辑真实可用）
